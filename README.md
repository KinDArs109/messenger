# Мессенджер

Мессенджер для своих: серверы и каналы, личные сообщения, голос с показом экрана, звонки, приложение для Windows и Android. Работает на своей машине, без чужих облаков.

```
apps/server        Express 5 + Socket.io + Prisma
apps/web           React 19 + Vite + Tailwind 4
packages/shared    типы и схемы валидации для сервера и клиента
```

**Запуск:** `npm run dev` поднимает оба приложения. Клиент — **http://localhost:5173**

Vite проксирует `/api` и `/socket.io` на бэкенд, поэтому в браузере всё приходит с одного адреса: httpOnly-cookie работает без настройки CORS, а среда разработки совпадает с боевой.

## База данных

PostgreSQL 18 развёрнут **локально**, из архива бинарников — без установщика, без службы Windows и без прав администратора. Каталог задаётся переменной `PGSQL_HOME`, данные лежат в `data` рядом с бинарниками.

Сначала база была в облаке (Neon): так было проще начать, когда локально поставить PostgreSQL не получалось. Оказалось, что это встроенная в архитектуру зависимость от заграничного канала — рвётся он, и мессенджер мёртв **для всех**, а не только для того, у кого стоит сервер. Поэтому база вернулась на ту же машину, что и сервер.

Раз службы нет, базу нужно поднимать самому:

```bash
npm run db:up
```

| Команда | |
|---|---|
| `npm run db:up` | поднять базу |
| `npm run db:down` | остановить |
| `npm run db:status` | проверить |
| `npm run check:db` | 40 запросов подряд — не рвётся ли соединение |

Путь к бинарникам переопределяется переменной `PGSQL_HOME`.

| `npm run check:realtime` | 11 проверок WebSocket — требует запущенного сервера |
| `npm run check:screen` | 5 проверок показа экрана — требует запущенного сервера, учётные записи заводит и убирает сама |

| `npm run db:cleanup` | убрать брошенные вложения и файлы без записей |
| `npm run db:password -- почта@example.com` | задать новый пароль учётной записи |

> **Про смену пароля.** Забытый пароль восстановить невозможно — в базе лежит только его хеш. Единственный выход — задать новый. Скрипт спрашивает пароль интерактивно и не печатает его на экране; аргументом передавать нельзя намеренно: командная строка видна в списке процессов и остаётся в истории оболочки. Все активные сессии при смене отзываются.

> **Про разрушительные команды.** `db:seed` стирает базу целиком, включая настоящие учётные записи. Он останавливается, если находит пользователей, которых нет в сидах, — продолжить можно только через `-- --force`. `db:cleanup` по умолчанию трогает лишь заведомый мусор; полная зачистка до состояния сидов — через `-- --hard`.

## Что уже работает

**Аутентификация.** Регистрация, вход, обновление и отзыв сессии.

Вход принимает и почту, и имя пользователя — одним полем, а не переключателем: человек не обязан помнить, чем он регистрировался. Различаем по собаке, в логине её быть не может.

**Имя пользователя задаётся один раз и не меняется.** По нему упоминают в сообщениях, находят в друзьях и входят. Смена рвала бы всё это разом: старые упоминания указывали бы в пустоту, а освободившийся логин мог бы занять кто угодно и начать получать чужие уведомления.

**Регистрация закрыта кодом.** Адрес мессенджера виден в интернете, поэтому открытая регистрация означала бы, что учётную запись заведёт любой, кто узнал ссылку. Код задаётся в `SIGNUP_CODE`; пока строка пуста, регистрация открыта — это осознанное поведение по умолчанию для запуска на своей машине, но для публикации наружу код обязателен.

Годится и общий код, и код действующего приглашения: человеку, которому прислали ссылку на сервер, вводить ничего не придётся — код подставится из адреса. Приглашение при этом только проверяется, а расходуется позже, когда человек реально вступает. Сравнение общего кода — `timingSafeEqual`: по времени обычного сравнения короткая строка подбирается посимвольно.

**Вход — в два шага.** Пароль отвечает ровно на один вопрос: знаете ли вы секрет. Секреты утекают, и почти никогда отсюда — а с других сайтов, где пароль оказался тем же. Поэтому после пароля сервер не пускает внутрь, а отправляет шесть цифр на почту: сессии на первом шаге нет ни в токене, ни в cookie.

Первый шаг возвращает пропуск — подписанный сервером на пятнадцать минут, с отдельной пометкой получателя. Пометка не даёт предъявить его вместо обычного токена и войти, минуя письмо. Второй шаг принимает пропуск и код вместе: одного кода мало, потому что тогда хватило бы знать чужой логин и угадать шесть цифр, пока хозяин входит.

Действующий код новым не заменяется. Человек нажал «войти», получил письмо, отвлёкся, вернулся, нажал ещё раз — и код из открытого у него письма всё ещё подходит; новое письмо приходит только по кнопке «отправить ещё раз». Адрес на экране показан наполовину закрытым (`iv•••••@почта`): до этого шага доходит и тот, кто знает чужой пароль, и дарить ему ещё и почту незачем.

Письмо при этом полезно само по себе. Код, пришедший тому, кто никуда не входил, — это сообщение «ваш пароль знает кто-то ещё», и приходит оно раньше, чем этот кто-то успевает прочитать переписку. Текст письма про это прямо и говорит.

Ответ не ждёт почтового сервера: код выдаётся и кладётся в базу, письмо уходит следом. Иначе вход застревал бы ровно настолько, насколько задумался почтовый сервер, — на недоступном адресе это десятки секунд.

Проверок шестнадцать: `npm run check:login -w @messenger/server`. Главная из них — не «код подходит», а «без кода не пускают».

**Подтверждение почты.** После регистрации — и при входе, если почта ещё не подтверждена, — на адрес уходит шестизначный код. Без него внутрь не пускают: вместо мессенджера показывается экран с полем для кода, а сервер отвечает отказом на всё, кроме раздела входа. Полоска-напоминание тут была раньше, и её закрывали; толку от неё немного — адрес, который никто не проверял, подводит ровно тогда, когда нужен: при потере пароля.

Запертым навсегда при этом не остаётся никто. Пока почта на сервере не настроена, застава молчит вовсе — иначе одна забытая строка в `.env` выключила бы мессенджер всем. Адрес меняется прямо с этого экрана, по паролю: опечатка в одну букву при регистрации иначе была бы приговором. А на случай, когда и адрес неверный, и пароль забыт, ключ есть у хозяина сервера — `npm run db:verified -w @messenger/server -- <логин>`; кнопки в интерфейсе для этого нет намеренно.

Заперты обе двери, а не одна: запросы и сокет. Закрыть только API бесполезно — сообщения, разговоры и «кто в сети» идут сокетом, и непроверенный просто зашёл бы с другой стороны. Проверяется это `npm run check:verify -w @messenger/server`: семнадцать проверок на временных учётных записях, которые убираются за собой.

Код лежит в базе хешем, как и всё, что даёт доступ: дамп не должен позволять войти чужой учётной записью. Живёт пятнадцать минут, пять попыток, между отправками минута — иначе кнопка «отправить ещё раз» превращается в способ засыпать чужой ящик с нашего адреса.

Настройки SMTP необязательны. Без них сервер стартует и работает как раньше: делать их обязательными значило бы ронять весь мессенджер из-за забытой строки в `.env`. Рекомендуемый отправитель — Яндекс: российский, бесплатный, работает без VPN. В `SMTP_PASS` нужен **пароль приложения**, а не пароль от ящика.

**Забыли пароль.** Код приходит письмом, дальше человек задаёт новый — «вспомнить» пароль невозможно, в базе только хеш.

Ответ на запрос кода всегда одинаковый, даже если такой учётной записи нет: иначе форма превращается в способ проверять, зарегистрирован ли конкретный адрес. По той же причине все ошибки на шаге проверки кода дают один текст — разные подсказали бы, на каком шаге подбор идёт правильно.

Успешная смена отзывает все сессии: восстановление пароля чаще всего означает «кто-то мог зайти», и оставлять чужие входы живыми нельзя. Заодно подтверждается почта — человек только что доказал, что письма до него доходят.

Кода из письма, а не ссылки: ссылка требует, чтобы почта открывалась на том же устройстве, где стоит приложение, а шесть цифр можно переписать с телефона руками.

**Вход по одноразовому коду** — второй способ, когда пароль забыт, а почта недоступна. Обычный TOTP из RFC 6238: Google Authenticator и любое совместимое приложение. Реализация своя, тридцать строк на `node:crypto`, — алгоритм не меняется десятилетиями, а зависимость пришлось бы обновлять и доверять ей секрет учётной записи.

Это не второй фактор, а запасной первый, и это осознанный размен: подключая коды, человек соглашается, что доступ к его телефону равен доступу к учётной записи. Поэтому отключение требует пароля — снять защиту тем же кодом мог бы и тот, кто вошёл по украденному.

Секрет создаётся на шаге настройки, но включённым становится только после подтверждения кодом: иначе не успевший добавить ключ остался бы со способом входа, которым не может воспользоваться. Допуск по времени — ±30 секунд: каждый лишний шаг втрое удлиняет окно жизни украденного кода.

- Пароли — Argon2id (пакет с готовыми бинарниками, Build Tools не нужны)
- Access-токен — JWT на 15 минут, живёт только в памяти клиента
- Refresh-токен — в httpOnly-cookie, в базе лежит лишь его SHA-256
- Ротация: при каждом обновлении старый токен отзывается
- Вход с несуществующей почтой занимает столько же времени, сколько с неверным паролем — иначе по задержке ответа можно перебрать, какие адреса зарегистрированы

**Реальное время.** Socket.io с проверкой токена на handshake: неопознанный сокет не создаётся вообще. Комнаты `user:`, `server:`, `channel:`. Статусы «в сети» считают количество вкладок, поэтому закрытие одной из трёх не выкидывает вас в офлайн.

**Общая защита.** Ограничение частоты запросов (жёстче всего на входе), helmet, CORS на один origin, валидация тел запросов через zod, единый формат ошибок.

**Непрочитанное и упоминания.** Каналы с новым выделяются жирным и белой меткой слева, упоминания дают красный счётчик на канале и на сервере в рейле, в ленте появляется черта «новые сообщения». Метка прочтения двигается только вперёд — иначе прокрутка вверх по истории «разчитывала» бы канал обратно.

Упоминания считает сервер, а не клиент: иначе любой мог бы наставить себе и другим любые счётчики. Упомянуть можно только того, кто и так видит канал. Правило разбора `@username` лежит в общем пакете — по нему сервер решает, кому увеличить счётчик, а клиент решает, что подсветить; разойдись они на символ, подсветка была бы там, где уведомления нет.

Отдельное лёгкое событие `channel:activity` доходит до всех участников сервера, а не только до подписчиков канала: без него непрочитанное было бы видно лишь там, куда человек и так смотрит.

**Ответы и реакции.** Ответ показывается одной строкой-цитатой над сообщением, клик по ней прокручивает к оригиналу. Удалённый оригинал не превращается в пустоту — цитата честно говорит, что сообщение удалено. Реакции приходят как «кто, к чему, что», а не готовой сводкой: признак «я тоже нажал» у каждого свой.

**Файлы.** Прикрепить можно кнопкой, перетаскиванием или вставкой из буфера. Загрузка идёт сразу при выборе, пока человек дописывает текст. Картинки показываются в ленте и открываются по клику, остальное — карточкой со скачиванием.

Тип определяется **по содержимому файла**, а не по расширению и не по тому, что заявил браузер: и то, и другое подделывается тривиально. Всё, кроме картинок, отдаётся с `Content-Disposition: attachment` и `CSP: sandbox` — присланный пользователем HTML не должен исполниться в нашем домене и добраться до чужой сессии. Имя на диске генерируем сами, пользовательское только показываем.

**Личные сообщения.** Клик по участнику в списке справа открывает переписку. Личный канал — это тот же `Channel`, только без сервера, с таблицей участников: вся логика сообщений, прав и сокета работает для него без единой правки. Повторный клик открывает существующую переписку, а не заводит новую. Собеседнику она появляется в списке сразу, без перезагрузки.

**Друзья.** Единственный способ начать переписку, не имея общего сервера: раньше написать можно было только тому, кого видишь в списке участников, то есть знакомство всегда начиналось с чужого сервера.

Заявка отправляется по имени пользователя, а не по идентификатору: идентификаторы наружу не показываются нигде, и человеку неоткуда их взять, а логин он видит в упоминаниях и может просто спросить.

Дружба хранится одной строкой на пару, а не двумя зеркальными — две пришлось бы согласовывать вручную, и рано или поздно они разошлись бы: у одного друг есть, у другого нет. Направление заявки считает сервер, каждой стороне уходит свой вариант.

Встречная заявка засчитывается как согласие: заставлять двоих, которые одновременно добавили друг друга, ещё и жать «принять» — бессмысленная церемония. Принять заявку может только адресат, иначе отправитель заводил бы дружбу в одностороннем порядке. Отклонённые не хранятся — строка удаляется, иначе попросить второй раз стало бы невозможно.

**Настройки.** Окно с тремя вкладками: профиль (имя и логин), внешний вид, вход. Настройки внешнего вида лежат в localStorage, а не на сервере: компактная лента уместна на большом мониторе и мешает на ноутбуке, тащить такое между устройствами вредно.

Вкладка «Вход» показывает устройства с активной сессией и даёт отозвать любое, кроме текущего — отзыв текущего был бы выходом, замаскированным под управление устройствами. Ни токена, ни его хеша наружу не уходит: список открывается в браузере, а токен даёт полный доступ к учётной записи. Чужую сессию по подобранному идентификатору не отозвать — поиск идёт строго среди своих, и ответ 404.

**Голосовые каналы.** Клик по голосовому каналу сразу подключает к разговору — заходить в «пустую комнату», а потом искать кнопку «войти» было бы лишним шагом там, где смысл канала ровно один. Состав виден в сайдбаре под каналом, у говорящего подсвечивается аватар, выключенный микрофон помечается. Полоска разговора живёт над панелью пользователя и не исчезает при переходе в другой канал: выйти должно быть можно всегда.

Звук идёт **напрямую между участниками** (WebRTC), сервер его не касается — только сводит людей и передаёт служебные сообщения. Разговор впятером не грузит ноутбук ничем, кроме пары десятков килобайт переписки о том, как соединиться.

**А вот картинка идёт через сервер, и это осознанный разворот.** Показ экрана «каждому свой поток» означает, что показывающий кодирует его столько раз, сколько людей в канале: вчетвером — трижды. Замер на боевом ноутбуке (`npm run check:share -w @messenger/desktop`, одна и та же движущаяся картинка в три соединения сразу) показал, чем это кончается: при нехватке полосы кодировщик роняет и размер, и кадры одновременно — 1080p превращается в 640×360 при пятнадцати кадрах. Никакими настройками это не лечится: надо перестать отправлять втрое больше нужного.

Теперь показ уходит **один раз**, а размножает его сервер ([realtime/sfu.ts](apps/server/src/realtime/sfu.ts) на mediasoup). Пережимать он ничего не пережимает — пакеты идут как есть, меняются только ключи шифрования, у каждого получателя свои. На машине с одним ядром это стоит немного, а домашнему каналу становится втрое легче. Голос при этом остался прямым: он весит копейки, а через сервер это лишние миллисекунды там, где их слышно.

Раздача **необязательна**. Библиотека родная, собирается под конкретную систему, и там, где её нет, сервер честно скажет «раздачи нет», а мессенджер вернётся к прежнему способу — незаметно для человека. Ему же достаётся и запасной путь по TCP для тех, у кого режут UDP.

```bash
npm run check:sfu -w @messenger/desktop
```

Одиннадцать проверок в трёх настоящих окнах мессенджера: вход, голосовой канал, включённая камера. Проверяется не только «картинка дошла до обоих», но и главное — **что ушла она один раз**, а не каждому своя; и что вошедший позже показывающего сразу видит показ, а не чёрный прямоугольник. Сама камера в проверке рисованная: встроенная поддельная камера Chromium на этой машине живёт ровно секунду, и мессенджер честно прекращает показ, считая, что камеру выдернули.

```bash
npm run check:sfu-server -w @messenger/server
```

Восемь проверок со стороны сервера — то, что ломается при переезде на другую машину: поднялась ли раздача, выдаётся ли дорога, стоит ли в приглашении настоящий адрес (а не `0.0.0.0`, на котором однажды всё и повисло молча) и те ли порты, что открыты в файрволе. Порты — `40000–40059/udp`, их надо открыть.

Схема «каждый с каждым», без SFU: на десяток друзей это правильный размен — задержка минимальная, а сводить потоки в один негде. На больших компаниях трафик у каждого рос бы линейно, и тогда понадобился бы отдельный сервер.

Список ICE-серверов отдаёт бэкенд, а не зашит в клиенте: появится TURN — его добавят строкой в `.env`, без пересборки клиента и обновления `.exe` у друзей.

**Усилитель голоса живёт внутри шумодава.** У одного друга гарнитура шепчет: на общей громкости его не слышно, а ручной ползунок упирался в 200% и всё равно не вытягивал. Причина была не в ползунке — вместе со своим шумодавом мы выключаем автоусиление браузера, потому что оно тянет вверх и шум в паузах, после чего чистить уже нечего. Получилось честно, но тихо.

Первым решением было сжатие (`DynamicsCompressor`) отдельным узлом. Измерение его и похоронило: тихий голос +22 дБ, фон в паузах — те же +22 дБ. Сжатие не умеет отличать речь от тишины, оно поднимает всё, что ниже порога. Такой усилитель называется «шумит».

Усиление переехало внутрь шумодава, потому что отличать речь от паузы умеет ровно он — дно шума он и так считает по каждой полосе. Громкость подтягивается **только по речевым кадрам**, к паузам применяется то, что насчитано на речи; тянем к −21 дБ, не больше восьмикратного. Вверх медленно (полсекунды), вниз быстро — иначе первое слово после долгой паузы прилетает ударом.

Измерено на настоящем коде воркера, теми же блоками по 128 (`npm run check:amplify`): тихий голос **+14,4 дБ**, обычный — **0 дБ**, разрыв между речью и тишиной **47,6 дБ до и после**, в паузах −70 дБ, потолок не задет. Обычного человека усилитель не трогает вовсе — ему и не нужно.

Потолки ручных регуляторов подняты заодно: общий и микрофонный до 300%, личная громкость собеседника до 500% — именно ею вытягивают того самого тихого, не делая громче всех разом. Такие числа безопасны только потому, что в конце цепочки стоит ограничитель: без него усиление доводит громкие слоги до предела цифры, а предел цифры звучит как треск.

**Качество связи** показано тремя значками — зелёный, жёлтый, красный, — и они отличаются не только цветом, но и числом полосок: каждый двадцатый мужчина не различает красный и зелёный. Рядом стоит число в миллисекундах, чтобы не наводить мышь.

Меряется задержка **до собеседника**, а не до сервера: сервер в разговоре не участвует вообще, и его пинг ничего не говорит о том, как слышно. Значение берётся из статистики WebRTC по выбранной паре адресов. Из нескольких соединений показывается худшее: если из четверых один слышен с задержкой, разговор испорчен у всех. Границы — 100 и 250 мс: до ста задержку не замечают, после двухсот пятидесяти начинают перебивать друг друга.

**Показ экрана — 30 кадров в секунду.** Не «сколько получится»: без явного потолка браузер выдаёт до шестидесяти, и на домашней отдаче четверым сразу картинка запаздывает. Потолок ставится дважды — при захвате и в самом кодировщике, потому что ограничение на захвате соблюдается не всегда. Там же стоит `degradationPreference: maintain-framerate`: при нехватке канала жертвовать надо чёткостью, а не плавностью — замыленный, но живой экран читается, дёргающийся нет.

Изображение идёт напрямую, как и звук. Через сервер проходит только объявление «показываю, поток называется так-то». Объявление обязательно: у получателя дорожки одного потока приходят порознь и в непредсказуемом порядке, и отличить экран от микрофона по наличию картинки нельзя — поток успевает побывать «без видео» ровно перед тем, как стать экраном. Поэтому имя потока объявляется **до** того, как пойдут кадры, и хранится в составе канала: вошедший позже сразу видит, что показ уже идёт, а не ждёт, пока показывающий выключит и включит.

Звук с экрана захватывается вместе с картинкой — показывают обычно то, что и звучит.

> **Честное ограничение.** Пока настроен только STUN, а он лишь подсказывает компьютеру, как тот выглядит снаружи. Когда оба собеседника за CGNAT — а у домашних провайдеров это норма, — прямой путь находится не всегда, и разговор может не состояться. Лечится TURN-ретранслятором, которому нужен сервер с белым IP. Это та же стена, что и с публикацией.

**Что можно делать в клиенте.** Создать сервер и каналы, пригласить по ссылке, писать в личку, писать, править и удалять сообщения, скрывать список участников, выйти. Правка чужих сообщений запрещена всем, включая владельца; удалять чужое может модератор.

**Модерация.** Правая кнопка на участнике — «Выгнать» и «Забанить». Спрятано в меню намеренно: действия редкие и необратимые, и им нечего делать там, где палец промахивается по «написать».

Кик и бан разведены и по смыслу, и по правам: выгнать — это «уйди сейчас», забанить — «не возвращайся». Кик ничего не запрещает, выгнанный вернётся по той же ссылке; бан — отдельная запись, которая переживает выход и проверяется до всего остального при переходе по приглашению. Иначе бан не значил бы ничего.

Трогать можно только тех, кто ниже по роли, и никогда себя: «выгнать себя» — это выход, у него другая кнопка. Сообщения выгнанного остаются: переписка — общая история, и вычищать её задним числом значит переписывать разговор, в котором участвовали другие.

**Приглашения друзьям.** В том же окне под ссылкой — список друзей, которых ещё нет на сервере, и кнопка «Позвать» у каждого. Приглашение уходит обычным личным сообщением со ссылкой, а не отдельной сущностью «приглашение»: у получателя не появляется ничего нового, он видит сообщение от друга и переходит по ссылке ровно так же, как если бы её переслали из другого мессенджера. Ни новой таблицы, ни нового экрана — три существующих запроса подряд.

**Приглашения.** Ссылка вида `/invite/<код>` — единственный способ впустить кого-то на сервер. Предпросмотр открыт без входа: человек видит, куда его зовут, прежде чем заводить учётную запись, а после регистрации вступает без второго клика по ссылке. Срок жизни и число использований ограничиваются.

**Сообщения.** История с курсорной пагинацией по ULID (не OFFSET — он линейно замедляется с глубиной прокрутки), отправка, правка, мягкое удаление. Новое сообщение создаётся обычным POST и рассылается подписчикам канала через сокет.

### Работа без сервера

Выключен сервер — приложение всё равно открывается и показывает **последнюю переписку** с плашкой «Нет связи», а не пустой экран. Так же ведёт себя дискорд, и по той же причине: интерфейс, который открывается пустым, выглядит сломанным, даже когда сломан не он.

Сохраняет всё service worker. Ответы сервера — «сначала сеть, при обрыве кэш»: свежая переписка всегда важнее старой, кэш здесь только запасной путь. Присланные файлы — сразу из кэша: их имена ULID, содержимое под одним именем не меняется никогда.

**Всё про вход через кэш не проходит** — там токены, список сеансов и коды. Личность приходится держать отдельно, в `localStorage`, иначе приложение без сети показало бы форму входа поверх сохранённой переписки.

Различать «сервер отказал» и «сервер не ответил» обязательно, и это делает `isNetworkFailure`. В первом случае человека действительно разлогинили — показывать ему сохранённое нельзя. Во втором сервер просто выключен, и переписка остаётся его собственной.

> **Сохранённое лежит на диске в открытом виде.** Пока вы не вышли из аккаунта, последняя переписка откроется без пароля у любого, кто откроет приложение на этом компьютере. Поэтому выход из аккаунта стирает и её, и запомненную личность — а не только токен.

Размеры ограничены: 200 ответов сервера и 300 файлов. Это последние дни общения, а не архив за год.

### Картинки

Присланные картинки пережимаются в **WebP на 90%** и хранятся только в таком виде. Скриншот 1920×1080 в PNG весит около 640 КБ, он же в WebP — около 210. Замерено на картинке с текстом и заливками, то есть на худшем для WebP случае; на фотографиях выигрыш больше.

Девяносто, а не восемьдесят: на фотографии и восемьдесят незаметны, но мелкий текст в скриншоте начинает мылиться, и присланный кусок кода становится нечитаемым. Это сжатие **с потерями** — обещать «качество не изменится» было бы неправдой, правильнее «разницу не видно».

**GIF не трогаем** — пережав, потеряли бы анимацию. Многокадровый WebP тоже пропускаем как есть.

Кроме оригинала делается **превью шириной 600 точек**, и в ленту едет оно. Раньше браузер честно скачивал всю картинку, чтобы нарисовать её шириной в палец: превью на порядок легче, а полную человек видит по клику. Плюс `loading="lazy"` — картинки выше по переписке не качаются, пока до них не долистают.

Отдельного поля в базе у превью нет: его ключ выводится из ключа оригинала, а нужность — из ширины. Если файла превью не окажется (загружено до появления этой возможности, или пережатие не удалось), раздача отдаёт оригинал — картинка на месте, просто тяжелее. Пустое место в ленте было бы хуже.

Разворот по метке EXIF делается при пережатии: снятое боком с телефона иначе так боком и показывалось бы.

## Публикация

**Сборка и запуск.** В продакшене клиент отдаёт тот же процесс, что и API, — один адрес, один порт, никакого CORS:

```bash
npm run build
```

```bash
npm run start
```

Адреса вроде `/invite/abc123` существуют только в браузере, поэтому всё, кроме `/api`, `/uploads` и `/socket.io`, отдаёт оболочку приложения. Иначе обновление страницы на приглашении давало бы 404.

**Устанавливается как приложение.** Есть манифест и service worker: Chrome и Edge предложат «Установить», и мессенджер откроется отдельным окном со своей иконкой в панели задач. Работает на Windows, Mac и Android одинаково — без `.exe`, без подписи кода, без предупреждений SmartScreen.

Service worker намеренно не кэширует скрипты и стили. Агрессивный кэш — классический способ намертво залипнуть на старой версии после выкладки; пока сервис обновляется по десять раз в день, цена такой ошибки выше выигрыша.

**Наружу — CloudPub.** У домашних провайдеров обычно CGNAT: роутер сам сидит за NAT, и проброс порта не работает. Туннель устанавливает соединение изнутри, поэтому белый IP не нужен.

Сначала пробовали Cloudflare Tunnel — он умирал через 47 секунд, потому что канал уходил за границу. CloudPub — российский аналог ngrok с российской же инфраструктурой, и по этой причине держится: **95 проверок за 312 секунд, ни одного сбоя**, задержка 65–160 мс.

Бесплатного тарифа хватает с запасом: постоянный поддомен (не меняется при перезапуске), автоматический сертификат Let's Encrypt, WebSocket, 250 ГБ трафика в месяц.

```bash
clo set token ВАШ_ТОКЕН
```

```bash
clo register http 3001
```

`register`, а не `publish`: зарегистрированные туннели поднимаются одной командой `clo run` — это и делает автозапуск.

> **Ссылку раздавать осторожно.** Регистрация в мессенджере открытая: аккаунт заведёт любой, кто получит адрес.

> **Проверять доступность надо на друзьях, а не на себе.** С включённым VPN вы смотрите на сервис из другой страны и о том, что увидят друзья, не узнаете ничего.

## Приложение для рабочего стола

```bash
npm run dist --workspace @messenger/desktop
```

На выходе два файла в `apps/desktop/release`:

| | |
|---|---|
| `Messenger-Setup.exe` | **рекомендуемый.** Ставится один раз в профиль пользователя, без прав администратора, сам создаёт ярлыки, обновляется сам |
| `Messenger-Portable.exe` | запускается без установки — для тех, кому нельзя ставить программы. Сам себя не обновляет |

Имена латиницей не для красоты: под ними же файлы лежат в `/updates`, откуда приложение забирает обновления, и под ними же они попадают в `latest.yml`.

**Как отдать файл другу.** Ссылкой на сам сервер: `/download` и `/download/portable`, без входа — иначе получался бы замкнутый круг, когда для установки приложения надо сначала в него войти.

Раньше выпуски уезжали ещё и в релизы на GitHub — как запасная дорога на случай, когда сервер выключен. Дорог стало две, и на вопрос «откуда качать» появилось два разных ответа; а главное, обновление приложения ходит всё равно в одно место. Теперь адрес один, тот же, по которому мессенджер и открывают.

Внутри тот же клиент, что открывается в браузере; отдельной сборки под десктоп нет и не нужно. Смысл оболочки в другом — своё окно, своя иконка в панели задач и отсутствие адресной строки, из-за которой приложение выглядит как сайт.

**Почему установщик, а не portable.** Portable-файл — это самораспаковывающийся архив: при **каждом** запуске он выкладывает 330 МБ во временную папку. Замеры на этой машине: portable — 6,4 с до окна, установленная версия — 0,8 с. Пять лишних секунд и треть гигабайта на диск каждый раз — слишком дорогая плата за «не надо устанавливать», поэтому portable остался запасным вариантом, а не основным.

Адрес сервера зашит по умолчанию, но лежит в `config.json` рядом с настройками пользователя и меняется из меню: туннель может переехать, и требовать ради этого пересборку у каждого друга — плохая идея.

### Чем приложение отличается от сайта

Раньше — ничем, кроме своей иконки и отсутствия адресной строки: оболочка просто открывала тот же сайт. Теперь разница в том, чего браузер не может **в принципе**, а не в том, что у сайта что-то отняли. Сайт остался полным: по нему друзья и пользуются.

| | приложение | браузер |
|---|---|---|
| Своя шапка окна с состоянием разговора | да | нет |
| Работа в трее после закрытия окна | да | нет |
| Счётчик непрочитанного на иконке в панели задач | да | нет |
| Системные уведомления с переходом в канал | да | нет |
| Запуск вместе с Windows | да | нет |
| Рация на глобальной клавише | да | **невозможно** |
| Выбор микрофона и динамиков | да | да |
| Показ экрана, звонки, всё остальное | да | да |

Выбор устройств специально сделан в обоих: это не различие, а недостающая функция, и оставлять браузерных пользователей без неё было бы просто недоделкой.

**Мост.** Всё это проходит через [preload.cjs](apps/desktop/preload.cjs) — единственное место, где странице достаются права, которых у сайта быть не должно. Мост появляется, только если страница загружена с того адреса, который оболочка считает своим: адрес меняется из меню, и отдать чужому сайту право вешать глобальные горячие клавиши и слать уведомления от нашего имени нельзя. Проверка живёт в самом preload, а не в главном процессе, потому что решать надо на месте, зная адрес именно этого документа.

По той же причине окно пересоздаётся при смене адреса сервера, а не просто грузит другой: разрешённый адрес задаётся один раз, при создании окна.

**Шапка.** `titleBarStyle: hidden` плюс `titleBarOverlay`: полоса наша, а кнопки свернуть-развернуть-закрыть остаются системными. Свои кнопки ломают Snap Layouts — раскладки, всплывающие при наведении на «развернуть», — и перетаскивание окна к краю экрана.

Шапка рисуется выше всего остального, включая экран входа. Сначала она стояла внутри и только у вошедших — окно нельзя было ни подвинуть, ни свернуть, пока не войдёшь, потому что системной полосы у него больше нет.

**Рация.** Честного «говорить, пока нажата» Electron не умеет: `globalShortcut` сообщает о нажатии и молчит об отпускании. Обходимся автоповтором — Windows шлёт горячую клавишу снова и снова, пока её держат, значит «отпустили» — это «повторы прекратились». Отсюда хвост в полсекунды: он же и не срезает концы слов. Если в системе выставлена большая задержка автоповтора, удержание будет срываться — на этот случай в настройках есть режим «переключать».

Клавиша занимается, только пока человек в разговоре: держать чужую F9 занятой всё время, что открыт мессенджер, невежливо по отношению к остальным программам.

**Проверки** — на настоящем `main.cjs`, а не на подделанном окружении:

```bash
npx electron scripts/test-bridge.cjs
```

Девять проверок моста, включая главную: на чужом адресе и на пустой странице моста быть не должно.

```bash
npx electron scripts/test-app.cjs
```

Десять проверок различий: окно, шапка, трей, значок, уведомления, рация, автозапуск.

### Автообновление

**Сам мессенджер обновляется без всего этого.** Оболочка грузит страницу с сервера, `index.html` отдаётся с `no-cache`, файлы — с хешами в именах. Любая правка интерфейса доезжает до всех при перезапуске окна, ничего выкладывать не надо.

Обновлять приходится только оболочку — и делает это `electron-updater`. Приложение проверяет GitHub через 20 секунд после запуска и дальше раз в шесть часов, качает в фоне и предлагает перезапуститься; отказались — обновление встанет при следующем закрытии. Есть и ручная проверка: меню → «Проверить обновления…».

Проверка молчит, когда обновлений нет или интернет моргнул: всплывающее окно посреди разговора раздражает сильнее, чем неустановленное обновление. Портативная сборка себя не обновляет — это один файл, подменить его на ходу нельзя.

Файлы берутся с GitHub, а не со своего сервера: обновление весит под сотню мегабайт, и гонять его через туннель — тратить общий канал ради того, что бесплатно раздаёт GitHub.

**Как выпустить версию.** Поднять `version` в `apps/desktop/package.json`, затем:

```bash
npm run release --workspace @messenger/desktop
```

Скрипт возьмёт токен у `gh` (в файле ключ от аккаунта не лежит), откажется перезаписывать уже выпущенный тег и соберёт с публикацией. В релиз уезжают установщик, его `.blockmap` и `latest.yml` — без последнего обновление не найдётся, а `.blockmap` позволяет докачивать только изменившиеся куски вместо всех ста мегабайт.

**Показ экрана в оболочке требует своего окна выбора.** В браузере его рисует сам браузер, в Electron его нет вовсе: без `setDisplayMediaRequestHandler` вызов `getDisplayMedia` молча не срабатывает, и кнопка показа экрана ничего не делает. Поэтому список источников собирает главный процесс, а выбирает человек в [picker.html](apps/desktop/picker.html) — отдельном окне со своим мостиком, потому что главному окну никаких дополнительных прав давать не за что. Звук системы берётся через `audio: "loopback"`.

Проверяется командой `npx electron scripts/test-capture.cjs` — она проходит весь путь и печатает, сколько кадров и какого размера получилось.

**Проверить обновление, не переустанавливая:**

```bash
npx electron scripts/test-update.cjs
```

Скрипт притворяется версией 0.0.1 и проходит весь путь друга: находит релиз, читает `latest.yml`, качает установщик и сверяет контрольную сумму. Смысл в том, чтобы поломка обнаружилась здесь, а не у человека, которому обновление тихо не приходит и он об этом даже не узнает.

**Проверить сам выпуск — после `npm run release`:**

```bash
npm run check:release -w @messenger/desktop
```

Тринадцать проверок и ни одной загрузки на сто мегабайт: объявление читается той же библиотекой, что и в приложении, контрольная сумма сверяется с собранным установщиком, сервер проверяется на отдачу кусками (без неё обновление качает все девяносто пять мегабайт вместо изменившихся), а внутри `app.asar` ищутся строки, ради которых выпуск и делался, — собраться из прошлой сборки установщик может совершенно молча.

Заодно проверяется вторая половина выпуска, про которую легко забыть: клиент на сервере. Оболочка и мессенджер внутри неё едут порознь, и «выпустил приложение, забыл выложить клиент» выглядит как «ничего не изменилось».

Один урок здесь уже оплачен: [dev-app-update.yml](apps/desktop/dev-app-update.yml) отстал от жизни — в нём остался заброшенный GitHub, куда выпуски уезжали раньше, — и проверка бодро докладывала про версию полугодовой давности, найдя её совсем не там, куда ходит приложение. Теперь берётся тот же файл, что лежит в собранном приложении.

Страница не получает доступа ни к Node, ни к внутренностям Electron (`contextIsolation`, `sandbox`, без `nodeIntegration`): оболочка не должна давать сайту больше прав, чем даёт обычный браузер. Переходы на чужие домены уходят в системный браузер — внутри окна без адресной строки из чужого сайта уже не выбраться.

> **SmartScreen будет ругаться.** Файл не подписан: сертификат подписи кода стоит десятки тысяч рублей в год. Друзьям придётся нажать «Подробнее» → «Выполнить в любом случае». Альтернатива без предупреждений — установка через браузер: Chrome и Edge предложат «Установить», и приложение появится отдельным окном со своей иконкой без единого `.exe`.

## Приложение для Android

Тот же сайт, открытый в своём окне без адресной строки, — [Trusted Web Activity](https://developer.chrome.com/docs/android/trusted-web-activity). Рисует его движок Chrome, уже стоящий на телефоне, поэтому весь apk — 900 КБ, а микрофон, разговоры и демонстрация работают ровно так же, как в браузере.

Обёртка вокруг WebView была бы толще и тише: свой движок, свои правила выдачи разрешений на микрофон и своё расхождение с браузером в тот день, когда что-то изменится в WebRTC. TWA — это буквально Chrome, только без вкладок.

```bash
cd apps/android && bubblewrap build --skipPwaValidation
```

На выходе `app-release-signed.apk` (для друзей) и `app-release-bundle.aab` (для Google Play). Первый сервер отдаёт по `/download/android`, и страница скачивания сама предлагает его тому, кто пришёл с Android.

**Обновляется вместе с сайтом.** Внутри — тот же адрес, поэтому пересобирать apk ради новой кнопки не нужно: достаточно выложить клиент. Новая сборка нужна, только если меняется само окно — имя, иконка, права.

### Ключ подписи

`apps/android/signing/messenger.keystore`, пароль рядом в `password.txt`.

Его нельзя терять и нельзя показывать. Android считает приложение своим по подписи: обновление, подписанное другим ключом, не встанет поверх — телефон потребует сначала удалить старое, а с ним уедут и данные. Копия ключа должна лежать там же, где резервные копии базы.

### Связь с сайтом

Чтобы Chrome убрал адресную строку, сайт обязан подтвердить, что приложение с такой подписью — своё. Подтверждение лежит в `apps/web/public/.well-known/assetlinks.json` и отдаётся отдельным маршрутом: `express.static` намеренно прячет пути, начинающиеся с точки.

Проверить, что связь видна снаружи, можно сервисом самого Google — тем же, которым пользуется телефон:

```bash
curl "https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://45.130.42.77.sslip.io&relation=delegate_permission/common.handle_all_urls"
```

Отпечаток в ответе обязан совпасть с отпечатком ключа:

```bash
keytool -list -v -keystore apps/android/signing/messenger.keystore -alias messenger
```

Не совпадут — приложение откроется, но с полосой адреса наверху, то есть вкладкой браузера.

> **Уведомления пока не приходят, когда приложение закрыто.** Разрешение у приложения есть, а веб-push на сервере не сделан: сообщение увидят, только открыв мессенджер. Это следующий шаг, а не поломка.

> **На айфоне приложения нет.** Отдельная сборка требует Mac и платного участия в программе Apple; для четверых это несоразмерно. iOS умеет ставить сайт на домашний экран сама: «Поделиться» → «На экран „Домой“» — открывается своим окном, без адресной строки. Страница скачивания это и предлагает, когда заходят с айфона.

## Панель управления

Ярлык **«Мессенджер»** на рабочем столе открывает панель: три индикатора состояния (база, сервер, туннель), кнопки запуска и остановки для каждого слоя, публичный адрес с копированием и переключатель автозагрузки. Ни одного окна консоли — все команды панель запускает скрытыми процессами.

WinForms из [scripts/panel.ps1](scripts/panel.ps1), а не Electron: панель должна открываться мгновенно и не тащить за собой полтораста мегабайт рантайма ради четырёх кнопок. Устанавливать нечего — всё уже есть в Windows.

**Крестик прячет окно в трей, а не закрывает приложение.** Панель остаётся фоновым процессом и продолжает показывать состояние в подсказке иконки. Настоящий выход — стрелка на панели задач, правая кнопка по иконке, «Закрыть».

Выход из панели не трогает сами сервисы. Это стоило отдельной правки: `Start-Process` привязывает запущенное к времени жизни родителя, и туннель умирал вместе с панелью — сайт отдавал 503, хотя база и сервер были живы. Поэтому сервисы стартуют через `WScript.Shell.Run`: так процесс остаётся жить сам по себе. Панель — пульт, а не хозяин.

Опрос идёт каждые две секунды и только локальными проверками — открытый порт, живой процесс. Любой сетевой запрос в этом цикле подвешивал бы интерфейс на время ответа.

**Кто зарегистрирован** — счётчик на панели и кнопка «Показать»: список имён пользователей, почт, подтверждена ли почта и включён ли вход по одноразовому коду. Читается прямо из базы, а не через сервер: административный вход в мессенджер — это ещё одна дверь наружу, в туннель, доступный всему интернету, а панель работает на этой же машине. Пароль от базы разбирается из `.env` и попадает в окружение только на время запроса.

Когда база выключена, панель пишет «неизвестно», а не ноль. Ноль означал бы, что все учётные записи исчезли, и причину полезли бы искать не там.

> Файл `panel.ps1` обязан лежать в **UTF-8 с BOM**. Windows PowerShell 5.1 читает скрипты без BOM в системной кодировке, и весь русский текст в интерфейсе превращается в мусор.

> **Кириллицу нельзя передавать внешним программам аргументом.** PowerShell отдаёт аргументы в системной кодировке, а не в UTF-8: русские буквы внутри SQL доезжали до Postgres битыми — `invalid byte sequence for encoding "UTF8"`. По той же причине пропадали кавычки вокруг `"User"`, а многострочный запрос не доезжал вовсе. Поэтому и запрос, и ответ ходят **файлами**, а сам SQL не содержит ни одной русской буквы: база отвечает единицами и нулями, словами их называет панель.

## Автозапуск

В автозагрузке Windows лежит ярлык не на сервисы, а на **саму панель** — [scripts/panel-boot.vbs](scripts/panel-boot.vbs). Она запускается скрыто, уходит в трей и поднимает всё остальное сама. Так у запуска один хозяин: состояние в трее с первой секунды соответствует действительности, а не догоняет чужой скрипт.

Порядок соблюдается по-настоящему: панель ждёт, пока база начнёт принимать соединения, и только потом стартует сервер. «Запустили» и «принимает соединения» — разные моменты, и на холодном старте между ними уходят секунды; без ожидания сервер падал бы и поднимался сторожем по второму кругу.

Планировщик заданий для этого не нужен: ярлык в автозагрузке работает без прав администратора и виден глазами, а не спрятан в системном реестре.

**Панель запускается в одном экземпляре.** Защита — именованный мьютекс: процессов `powershell.exe` в системе много, и отличить свой от чужого по имени нельзя. Повторный клик по ярлыку не заводит вторую иконку в трее, а показывает окно уже работающей панели — через именованное событие, а не поиск окна по заголовку: после запуска из автозагрузки окно не показывалось ни разу, дескриптора у него нет, и находить нечего.

**Перезапуск после падения** держит [scripts/serve-loop.ps1](scripts/serve-loop.ps1) — сторож на два десятка строк: запускает сервер, ждёт его завершения, поднимает заново. Пять падений подряд быстрее чем за полминуты — цикл останавливается, потому что бесконечный перезапуск только прячет причину.

Здесь раньше был `pm2`, и он работал. Убран по одной причине: его демон на Windows открывает собственное окно консоли, которое нечем спрятать и которое возвращается, если закрыть. Для приложения, которое должно тихо жить в трее, это неприемлемо, а всё, чем pm2 был здесь полезен, уместилось в цикл `while`.

Проверить вручную:

```bash
wscript scripts/panel-boot.vbs
```

> **Ноутбук не должен засыпать.** Спящая машина для друзей неотличима от выключенной. В параметрах питания поставьте «Никогда» для сна при работе от сети.

## Копии и сторож

На сервере два системных таймера. Оба ставятся один раз и дальше живут сами.

**Копии** — `messenger-backup.timer`, каждую ночь в 4:30. [deploy/backup.sh](deploy/backup.sh) снимает базу (`pg_dump`), загруженные файлы и `.env`, складывает в `/opt/backups` и удаляет всё старше двух недель. Сейчас всё вместе весит около 270 КБ.

Копия лежит на той же машине. Это защита от «удалил не то» и от порчи данных, но **не от гибели сервера**: чтобы копия пережила и его, её надо забирать наружу — на любую другую машину:

```bash
scp root@45.130.42.77:/opt/backups/db-*.sql.gz ./backups/
```

Проверить, что копия разворачивается (делать на пустой базе, не на боевой):

```bash
zcat /opt/backups/db-2026-08-07.sql.gz | psql restore_test
```

**Сторож** — `messenger-monitor.timer`, раз в минуту. [deploy/monitor.sh](deploy/monitor.sh) проверяет шесть вещей: отвечает ли мессенджер изнутри, открывается ли он снаружи по HTTPS, жива ли база, слушает ли ретранслятор голоса свой порт, сколько осталось диска и памяти.

Пишет только на смену состояния. Сторож, который шлёт «всё хорошо» шестьдесят раз в час, перестают читать через день, и настоящую тревогу в этом потоке уже не видно. Тревога уходит на второй неудачный прогон подряд, а не на первый: сеть моргает, служба перезапускается за секунды, и будить из-за этого некого.

**Сторож умеет отличать чужую беду от своей.** 17 августа он написал «мессенджер не работает» и назвал час простоя — которого не было: друзья всё это время сидели в приложении, а проверка нажатиями прошла через тот же публичный адрес целиком. Сломалось другое: у сервера на час пропало разрешение имён, и сторож не смог найти ни сайт, ни Телеграм — свою же тревогу он в тот момент отправить не сумел, она пришла задним числом вместе с «снова работает».

Поэтому при отказе внешней проверки тот же адрес запрашивается ещё раз в обход имён, по IP (`curl --resolve`). Отвечает — значит сайт жив, ослеп сторож, и в тревоге так и написано: **не работает DNS**, сайт открывается, но уведомления на телефоны уходить не будут — службе доставки тоже нужно имя. Ложная тревога хуже молчания: на неё перестают приходить.

Оттуда же второй урок: **у сервера теперь три резолвера вместо одного**. Провайдерский первым, `77.88.8.8` и `8.8.8.8` запасными, `options timeout:2 attempts:2` — при живом первом не меняется ничего, при мёртвом ответ приходит с запасного за пару секунд вместо получаса ожидания. Проверено с намеренно убитым первым: имя разрешается, сайт открывается, сторож молчит. Файл `/etc/resolv.conf` пишется cloud-init один раз (PER_ONCE) и переживает перезагрузку — но не пересоздание машины: если сервер когда-нибудь собирать заново, запасные адреса надо вернуть руками.

Время в сообщениях — московское, а не серверное: сервер живёт по UTC, и «лежал с 21:55» означало 00:55 по часам того, кто это читает.

Куда писать — задаётся в `/opt/messenger/monitor.env` (права 600, в git и в копии не попадает). Пока файл пуст, сторож работает и пишет всё в журнал, просто молча:

```bash
journalctl -u messenger-monitor -n 20 --no-pager
```

Проверить тревогу целиком — погасить службу и подождать две минуты:

```bash
systemctl stop messenger && sleep 130 && systemctl start messenger
```

Должно прийти «🔴 Мессенджер не работает» со списком причин и хвостом журнала, а после подъёма — «✅ Мессенджер снова работает».

**Чего сторож не поймает — гибель самой машины.** Мёртвый сервер не может сообщить, что он мёртв. Для этого нужна проверка снаружи: любой бесплатный сервис отслеживания, который дёргает

```
https://45.130.42.77.sslip.io/health
```

раз в пять минут и ждёт кода 200 (ответ — `{"ok":true,"uptime":…}`).

Оба скрипта и разбор системных таймеров лежат в [deploy/](deploy/) — на сервере они живут в `/opt/messenger/`, но если машину придётся пересобирать, восстанавливать их неоткуда, кроме репозитория.
